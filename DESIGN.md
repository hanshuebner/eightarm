# RP2350-based PDP-8 Omnibus Interface Card — Design Document

## 1. Summary

The card occupies a single PDP-8/E Omnibus slot and answers both **memory
cycles** and **IOT cycles**:

* Memory cycles — emulates up to 32 KW (8 fields × 4 KW) of core memory and
  optionally a ROM image overlay.
* IOT cycles — emulates one or more serial-line peripherals (PT08-style
  asynchronous keyboard/teleprinter pairs) plus a console/control interface
  used by the host PC for memory upload/download and front-panel emulation.
  Additional devices (disk, DECtape, line printer, etc.) are added by
  registering new device codes in the firmware dispatch table.

The active digital content of the card is a single Raspberry Pi RP2350B
microcontroller in the PGA2350 module form-factor. The Omnibus side uses
74244 input buffers and 74540 inverting output buffers to bridge between
the bus's negative-true 0/+3 V signaling and the RP2350's 3.3 V CMOS GPIO.
Octal latches between the buffers and the RP2350 let the MD bus and the
DATA bus share a single 12-bit RP2350 GPIO port. Slow signals are absorbed
by two MCP23017 I²C port expanders (console set-and-hold and
on-board housekeeping); a 4× 74HC597 shift-register chain plus a
74HC273 pulse-latch bank captures the remaining slow signals
(including short pulses like TPx, INT_STROBE, LINK_LOAD and the
end-of-cycle phase signals INHIBIT and RETURN) at full bus rate
for cycle-accurate trace (§6.10).

The host PC sees a single USB device exposing several CDC ACM endpoints.
One endpoint is the control/console port; the remaining endpoints are
virtual TTYs corresponding to the emulated serial peripherals.

2. **Bus buffers** — 74AHC244 input banks (non-inverting) and 74AHCT540

3. **74AHC574 octal latches** — MD-IN, DATA-IN, MD-OUT, DATA-OUT, IOT-

4. **RP2350B (PGA2350)** — 12-bit shared D-port + 33 fast GPIO + 1 spare,
   PIO ×3, dual Cortex-M33, 520 KB SRAM, 16 MB flash.
5. **USB-C → host PC** — composite CDC: CDC0 console, CDC1..N virtual
   TTYs.

To the right of the RP2350 sit the I²C subsystem (2× MCP23017 + up to
4× SC16IS740 UART, all on I²C0 at 1 MHz fast-mode-plus) and the
optional per-port-modular RS-232 add-on (1–4× MAX3232 + DB9).

### 2.2 Bill of materials (active digital)

Mandatory population (memory + IOT + USB console):

* 1× RP2350B in PGA2350 module — processor, RAM, flash, USB
* 74AHC244 (or equivalent) octal non-inverting tri-state buffers —
  input from Omnibus
* 74AHCT540 (or equivalent) octal inverting tri-state buffers —
  output to Omnibus, including one bank dedicated to console-mode
  drives (§4.4)
* 4× 74AHC574 octal edge-triggered latches — MD-in, DATA-in, MD-out,
  DATA-out bus sharing
* 1× 74AHC574 — IOT response latch (SKIP, C0, C1, C2 plus 4 spare)
* 4× 74HC597 octal parallel-load shift registers (dual-stage:
  separate storage register and shift register) — slow-signal trace
  chain, storage clocked at TS1-rising, shifted by PIO during
  TS2..TS4 (§6.10)
* 1× 74HC273 octal D-FF with /CLR — pulse-latch bank for short
  pulse and phase signals (TP1..4, INT_STROBE, LINK_LOAD, INHIBIT,
  RETURN); accumulates pulses during a cycle, sampled into the trace
  chain at end-of-cycle, reset by a brief RC-differentiated pulse off
  TS1 (§6.10)
* 2× MCP23017 16-bit I²C GPIO expanders at I²C addresses 0x22..0x23 —
  bidirectional console-mode outputs (§4.4) and on-board housekeeping
  (status LEDs, reset button, board-ID straps, indicator drives).
  The two former observe-only expanders at 0x20/0x21 are removed:
  the slow signals they covered are now captured at full bus rate by
  the §6.10 trace chain.
* Omnibus 144-pin edge connector
* +3.3 V LDO regulator (e.g. AMS1117-3.3 or MIC5219-3.3)
* Pull-up/-down networks on slow signals
* USB Type-C receptacle
* microSD card socket (push-push, 8-pin) with ESD protection — for bulk
  storage of disk images, memory snapshots, and configuration (§7.6)

Optional population (physical RS-232 ports — see §7.4):

* 1–4× SC16IS740 single-channel I²C UART, each at a distinct I²C
  address from 0x48..0x4B (strap-selected via A0/A1 per chip). Populate
  one chip per RS-232 port — 1, 2, 3, or 4 ports per board as needed.
* 1–4× MAX3232 (or SP3232) 3.3 V RS-232 transceivers — one per
  populated UART chip
* 1–4× DB9 male right-angle PCB connectors (or 2×5 IDC headers as
  alternate footprint) — one per populated port

12-bit Omnibus words fit in 8-bit-wide latches if two are paired per
direction (8 + 4 = 12); 9-bit parts (74AHC821-class) can also be used.
Footprint choice is left to PCB layout; this document treats them as
logical 12-bit latches.

### 3.2 Memory address — MA0..MA11, EMA0..EMA2 (15 signals)

| Pin | Net | Pin | Net |
|---|---|---|---|
| AD1 | ~MA00 | DD1 | ~MA08 |
| AE1 | ~MA01 | DE1 | ~MA09 |
| AH1 | ~MA02 | DH1 | ~MA10 |
| AJ1 | ~MA03 | DJ1 | ~MA11 |
| BD1 | ~MA04 | AD2 | ~EMA0 |
| BE1 | ~MA05 | AE2 | ~EMA1 |
| BH1 | ~MA06 | AH2 | ~EMA2 |
| BJ1 | ~MA07 |     |       |

MA0..MA11 give 4 KW of word-addressable memory per field; EMA0..EMA2 select
one of 8 fields (the standard PDP-8/E KM8-E memory-extension scheme), giving
32 KW maximum.

EMA0..EMA2 are **not** the CPU's internal IF or DF registers — they are the
output of a per-cycle multiplexer driven by KM8-E that selects:

* `EMA = IF` during instruction fetch (IFETCH) and indirect-address fetch
  (DEFER) cycles
* `EMA = DF` during direct data read/write (EXECUTE) cycles
* `EMA = 0` (forced) during interrupt entry

The IF and DF registers themselves only change when the program executes
CDF/CIF/CIDF (or the front panel manipulates them), but the EMA bus signal
the card sees can change on every memory cycle: a single memory-reference
instruction with indirect addressing produces three consecutive memory
cycles whose EMA values are `IF, IF, DF` at ~1.5 µs each. EMA settles
before TS1 alongside MA and must be sampled with the same timing as MA.
For this reason EMA0..EMA2 are routed to direct RP2350 GPIO, not to a port
expander.

### 3.3 Memory data — MD0..MD11 (12 signals, bidirectional)

| Pin | Net | Pin | Net |

| AK1 | ~MD00 | BL1 | ~MD05 |

## 4. Signal Routing in the New Design

### 4.1 Fast / direct RP2350 GPIO

The following signals are routed directly to RP2350 GPIO pins, with
appropriate level-translation through the existing 74244 / 74540 buffers.

A signal is classified **fast** if the card must observe or drive it
within a single Omnibus cycle (~1.5 µs) to participate correctly —
typically meaning it carries cycle-by-cycle data (MA, MD, DATA, TS
edges) or gates a response that must be valid by a specific timing
pulse (SKIP/Cx by TP2, INT_RQST deassertion within the acknowledging
IOT cycle). End-to-end latency from bus edge to firmware-visible value
is ~10–20 ns through the 74244 input buffer plus one PIO clock at
150 MHz.

A signal is classified **slow** (§4.2) if the card only needs it at
human-perceivable rates and is bidirectional or output-only — namely,
the set-and-hold console-mode outputs (§4.4) and on-board
housekeeping (status LEDs, reset button, board-ID straps, IND1/IND2
indicator drives). Slow-path signals reach the firmware via two
I²C-attached MCP23017 expanders with ~80 µs round-trip latency per
full poll, polled at 50 Hz by default and on-demand for console
queries.

Observation-only slow signals — major-state F/D/E, IR, link, break,
interrupt-acknowledge, TPx, etc. — used to live on a separate pair
of MCP23017 expanders (the original design's #0 and #1) but have
been migrated to the §6.10 cycle-accurate trace chain, which samples
them at full bus rate.

The 24 bus-data signals (MD0..MD11 and DATA0..DATA11) share a single
12-bit RP2350 port (`D0..D11`). The four 74AHC574 latches of §5
(MD-IN, MD-OUT, DATA-IN, DATA-OUT) decouple the two physical buses
from the shared port; memory cycles and IOT cycles are mutually
exclusive in time so the multiplexing is loss-less. MD and DATA
therefore appear in the table below only as the shared `D0..D11`
entry, but they contribute 24 of the 96 active Omnibus signals counted
in §3.11.

| Group | Signals | Pins | Direction |
|---|---|---|---|
| Address | MA0..MA11 | 12 | RP2350 in (CPU's CPMA always drives MA — see §4.4) |
| Extended address | EMA0..EMA2 | 3 | RP2350 in |
| Shared 12-bit data port | D0..D11 (carries MD0..MD11 in memory cycles, DATA0..DATA11 in IOT cycles) | 12 | bidirectional, latched both ways |
| Cycle qualifiers | MEM_START, IO_PAUSE | 2 | RP2350 in (INTERNAL_IO moved to trace chain — see §6.10; the firmware recognises internal IOTs from MD device-code 0..7) |
| Memory write strobe | WRITE | 1 | RP2350 in |
| Memory SOURCE | SOURCE | 0 | routed via the trace chain (§6.10) on the assumption §10 resolves to RP2350-input-only; if §10 instead resolves to bidirectional, SOURCE returns to direct GPIO and one of the MCP23017 #3 housekeeping signals takes its trace-chain slot |
| TS edges | TS1, TS3 | 2 | RP2350 in (TS2/TS4 derived in PIO) |
| IOT data strobe | BUS_STROBE | 1 | RP2350 in |
| Bus-direction control | MD_DIR | 1 | RP2350 out (to 74540 OE) |
| Output-latch enable (shared) | LE_OUT | 1 | RP2350 out, demuxed to MD_OUT or DATA_OUT by MEM_START vs IO_PAUSE |
| Input-latch enable (shared) | OE_IN | 1 | RP2350 out, demuxed to OE_MD_IN or OE_DATA_IN by MEM_START vs IO_PAUSE |

### 4.2 Slow / I²C MCP23017 port expanders

Two MCP23017s on I²C0 at addresses 0x22 and 0x23 cover the
bidirectional console-mode outputs (§4.4) and on-board housekeeping
(status LEDs, reset button, board-ID straps, indicator drives). The
former observe-only expanders at 0x20/0x21 — which provided ~50 Hz
visibility into major-state, IR, link, break, interrupt-acknowledge,
TPx, and similar slow signals — have been removed: those 32 signals
are now captured at full Omnibus rate by the §6.10 trace chain.
Non-volatile config lives in an internal RP2350 flash partition (no
separate EEPROM). The same I²C bus carries up to four optional
SC16IS740 single-channel UART chips (§7.4) at addresses 0x48..0x4B.

The bus is configured as I²C fast-mode-plus (1 MHz) so MCP23017
polling and SC16IS740 byte transfers do not contend. The 1 MHz figure
is the **bus clock rate**, not a sampling rate: a full poll of both
MCP23017s reads 4 bytes plus address/register overhead in ~80 µs.
The firmware polls at 50 Hz by default (every 20 ms — fine for state
display and console-status queries) and triggers an immediate poll on
console commands like `status`. Cycle-rate observation of bus state
no longer flows through this path — it is handled by the §6.10 trace
chain.

Several signals are **bidirectional**: they're observed when another module
is driving the bus, and asserted by the card during console operations
(§4.4). On the MCP23017 side, the same physical pin is reconfigured between
input and output via the IODIR register; on the bus side, a separate 74540
output channel under software-controlled OE provides the assertion path.

| MCP # | Pins | Signals | Notes |
|---|---|---|---|
| #2 (0x22) | A0..A7 | KEY_CTL, STOP, LA_ENABLE, DF_ENABLE, MS_DISABLE, CPMA_DISABLE, IND1, IND2 | **bidirectional** — set-and-hold console outputs (see §4.4); IND1/IND2 are output-only indicator drives migrated from the removed MCP #1 |
| #2 (0x22) | B0..B7 | OE_CONSOLE_HOLD, (7 spare) | OE for the set-and-hold half of the console-output 74540 bank |
| #3 (0x23) | A0..A7 | STATUS_LED_0, STATUS_LED_1, STATUS_LED_2, BOARD_RESET_BTN, BOARD_ID_0..3 | on-board housekeeping; LEDs out, button + ID straps in |
| #3 (0x23) | B0..B7 | (8 spare) | reserved for additional slow signals |

EMA0..EMA2 are **not** on a port expander — see §3.2. They sit on direct
RP2350 GPIO and are sampled by PIO at the same TS1 edge as MA.

The pulse-timed console outputs LOAD_CONT, PULSE_LA, INITIALIZE are also
not on an MCP23017 — their pulse-width requirements (~100–300 ns) are
incompatible with I²C latency. They are **not** on direct RP2350 GPIO
either; they are folded into the IOT response latch (see §4.4) and
gated onto the bus by `OE_CONSOLE_PULSE`.

The MCP23017 INTA/INTB lines are not used in this design — the firmware
polls the expanders at human-perceivable rates (typically 50 Hz) and on
specific events, which is far faster than human reaction time.

### 4.3 RP2350 GPIO budget summary

PGA2350 (RP2350B) has 48 user GPIO. USB and SWD are on dedicated pins and
do not consume GPIO.

| Use | Pins |
|---|---|
| I²C0 (SDA, SCL) — to 2× MCP23017 + optional SC16IS740 chips | 2 |
| Direct fast-path Omnibus signals (§4.1) | 44 |
| Trace chain (§6.10) — TRACE_SCK out, TRACE_SDI in | 2 |
| **Total** | **48** |

The 4-pin SD-card SPI sub-budget (§7.6) is funded by **folding the three
console pulse outputs** (`LOAD_CONT`, `PULSE_LA`, `INITIALIZE`) into the
IOT response latch path (§4.4), reclaiming 3 GPIO; the net change vs.
the no-SD design is +1 pin.

The 2-pin trace-chain sub-budget (§6.10) is funded by demoting two
signals out of the direct fast path: **INTERNAL_IO** (recoverable
from MD device-code decoding — internal IOTs use device codes 0..7)
and **SOURCE** (assuming §10 resolves to RP2350-input-only — if it
resolves to bidirectional, SOURCE returns to direct GPIO and a
spare position on MCP23017 #3 substitutes on the trace chain). Both
demoted signals remain visible to the firmware, sampled by the trace
chain on every cycle (§6.10) — the demotion does not lose
information, only the ability to trigger PIO on their edges, which
is not needed.

Status LED and on-board housekeeping live on MCP23017 #3 (§4.2),
which has ~16 spare pins for additional slow signals. If further pin
pressure arises later (e.g., BREAK-cycle support per §6.9), a slow
signal can be moved from MCP23017 #3 onto a freed RP2350 pin and a
less-critical fast signal demoted to MCP23017 #3 or to a spare
position on the trace chain — a firmware and routing change rather
than a BOM change.

The RP2350's HSTX block can alternatively absorb the shared D-port
output direction, freeing additional GPIO. That option is noted but
not used in this design.

### 4.4 Console-mode bus drives

When the host issues a console command via CDC0, the card temporarily takes
control of the Omnibus and asserts the same control signals that an M8330
timing module / M8650 front-panel module would assert. The data path for
console operations reuses existing hardware:

* **Address loading**: the card never drives MA directly. Instead it drives
  the desired address onto the **DATA bus** (the path the standard front
  panel uses for the SR — switch register), then asserts LA_ENABLE and
  pulses LOAD_CONT to load the CPU's CPMA register from the SR-mux. The
  DATA-OUT latch from §5 is reused.
* **Data deposit**: drives the desired word onto the **MD bus** via the
  existing MD-OUT latch path; pulses MEM_START with WRITE asserted by the
  CPU.
* **Memory examine** (for memory the card itself emulates): handled
  internally — no bus drive needed; the firmware reads its own SRAM image.

The control signals that flip from input-only to bidirectional:

| Signal | Type | Path on assertion |
|---|---|---|
| KEY_CTL | set-and-hold | MCP23017 #2 → 74540 → bus |
| STOP | set-and-hold | MCP23017 #2 → 74540 → bus |
| LA_ENABLE | set-and-hold | MCP23017 #2 → 74540 → bus |
| DF_ENABLE | set-and-hold | MCP23017 #2 → 74540 → bus |
| MS_DISABLE | set-and-hold | MCP23017 #2 → 74540 → bus |
| CPMA_DISABLE | set-and-hold | MCP23017 #2 → 74540 → bus |
| LOAD_CONT | pulse | IOT-RESP latch (bit 5) → 74540 pulse bank → bus |
| PULSE_LA | pulse | IOT-RESP latch (bit 6) → 74540 pulse bank → bus |
| INITIALIZE | pulse | IOT-RESP latch (bit 7) → 74540 pulse bank → bus |

The set-and-hold signals come from MCP23017 #2 output pins through a
74540 set-and-hold bank gated by an MCP23017 OE.

The three console pulses **share the IOT-response latch** with the IOT
response bits. The IOT-RESP `74AHC574` carries 8 bits: bits 1..4 are
the IOT response (SKIP, C0, C1, C2), bits 5..7 are the console pulses
(LOAD_CONT, PULSE_LA, INITIALIZE), bit 8 is spare. The two halves feed
**different** 74540 OE banks:

* Bits 1..4 → IOT-response 74540 bank, OE = `OE_IOT_RESP` (asserted only
  during IOT cycles, gated to TP2..TP4 window).
* Bits 5..7 → console-pulse 74540 bank, OE = `OE_CONSOLE_PULSE`
  (asserted only during halted-CPU console operations, for the strict
  duration of each pulse).

Sharing is safe because IOT responses (CPU running) and console pulses
(CPU halted) are **mutually exclusive in time**. To pulse `LOAD_CONT`,
the firmware writes the appropriate bit pattern to the shared D-port,
clocks the IOT-RESP latch via `LE_IOT_OUT`, and then briefly asserts
`OE_CONSOLE_PULSE` for ~200 ns. PIO drives the OE timing precisely.

This sharing reclaims **3 RP2350 GPIO pins** that were otherwise
dedicated to LOAD_CONT/PULSE_LA/INITIALIZE; those pins are spent on the
SD-card SPI interface (§7.6).

**Why bidirectional, not just output**: a real M8650 front panel (or
another diagnostic card) may be installed in the same backplane during
hardware development. Keeping the 74244 input path means the card
can sense external assertions of these signals and back off — the firmware
checks for external assertion before driving and can yield to a physical
front panel if one is present.

**Console-cycle sequence (Examine):**

```
  Firmware (Cortex-M33, called from CDC0 shell)
  --------------------------------------------------------
  1. Configure MCP23017 #2 pins as outputs; assert KEY_CTL,
     CPMA_DISABLE, LA_ENABLE; release STOP if running, hold STOP if examining.
  2. Drive target address onto shared D-port; pulse LE_OUT
     (demuxed to DATA-OUT since IO_PAUSE is not asserted).
  3. Assert the MCP23017 OE for the set-and-hold 74540 bank.
  4. Write bit pattern (LOAD_CONT bit set) to D-port; pulse LE_IOT_OUT
     to clock the IOT-RESP latch.
  5. Briefly assert OE_CONSOLE_PULSE for ~200 ns — the latched
     LOAD_CONT bit drives the bus through the pulse 74540 bank.
     CPMA loads from the DATA bus.
  6. Pulse MEM_START via the existing MEM_START output path
     (added to the same 74540 console bank); memory cycle runs.
  7. Card observes its own MD-OUT response (or external memory's MD)
     via the MD-IN latch. Captured value is returned via CDC0.
  8. Deassert all OEs; reconfigure MCP23017 #2 pins back to inputs.
```

**Console-cycle sequence (Set EMA / data field):**

```
  1. Drive desired field number on D-port bits 9..11 (mapped to EMA via
     the SR upper bits per KM8-E convention).
  2. Pulse LE_OUT to DATA-OUT latch.
  3. Assert DF_ENABLE + LA_ENABLE.
  4. Write PULSE_LA-bit pattern to D-port; pulse LE_IOT_OUT, then
     briefly assert OE_CONSOLE_PULSE; KM8-E loads IF/DF from upper SR bits.
  5. Release DF_ENABLE / LA_ENABLE.
```

(MEM_START is added to the console-output bank as a 10th signal, taking
one of the two spare positions on the new 74540 — only used in console
mode for forced cycles.)

### 4.5 What stays read-only

* **MA0..MA11** — driven by CPU CPMA at all times; loaded by the SR-via-
  DATA mechanism above.
* **EMA0..EMA2** — output of the KM8-E mux; loaded indirectly via DF/IF
  registers as above.
* **MD bus** *during memory READ* — driven by the card; *during memory
  WRITE* — driven by the CPU; the card never needs to drive MD outside
  its own emulated address space, so MD stays in the existing
  MD-OUT-only-when-reading pattern.
* **TS1..TS4, TP1..TP4** — always CPU-driven.
* **IR00, IR01, IR2, F, D, E, F_SET, USER_MODE** — always CPU-driven.

## 5. MD/DATA Bus Sharing — Latch Implementation

### 5.1 Topology

The card has two physical 12-bit buses to the Omnibus (MD and DATA) but only
needs one 12-bit RP2350 port because memory cycles and IOT cycles are
mutually exclusive in time. Five octal latches handle the multiplexing:

```
  ----------------------------------------------------------------------
  Direction   Path
  ----------------------------------------------------------------------
  IN  MD    : MD bus → 74244 → 74AHC574(MD_IN)  → tri-state → RP2350 D
              latch CK = WRITE strobe trailing edge
              tri-state OE = OE_IN gated by MEM_START (active low)

  IN  DATA  : DATA bus → 74244 → 74AHC574(DATA_IN) → tri-state → RP2350 D
              latch CK = BUS_STROBE trailing edge (when card is sink)
              tri-state OE = OE_IN gated by IO_PAUSE (active low)

  OUT MD    : RP2350 D → 74AHC574(MD_OUT) → 74540 → MD bus
              latch CK = LE_OUT gated by MEM_START
              74540 OE driven by MD_DIR

  OUT DATA  : RP2350 D → 74AHC574(DATA_OUT) → 74540 → DATA bus
              latch CK = LE_OUT gated by IO_PAUSE
              74540 OE gated by IOT C-codes + BUS_STROBE

  OUT IOT   : RP2350 D[3:0] → 74AHC574(IOT_RESP) → 74540 → SKIP, C0, C1, C2
              latch CK = LE_IOT_OUT
              74540 OE = OE_IOT_RESP, gated by IO_PAUSE + TP2 window
  ----------------------------------------------------------------------
```

### 5.2 Why latches and not just gated buffers

Latching at the bus side decouples Omnibus timing from RP2350 instruction
timing. A 74244-only multiplex would require the RP2350 to drive its
output port exactly when the bus needs the data, and to sample its input
port exactly when the bus presents valid data. With latches:

* For *outputs*, the RP2350 firmware computes the response value at any
  time during the cycle and clocks it into the latch. The latch's tri-state
  output is enabled by a separate signal at the right Omnibus phase.
* For *inputs*, the latch captures the bus value on a clean edge of WRITE
  or BUS_STROBE. The RP2350 reads the latch value at any time before the
  next cycle — there is no real-time sampling pressure.

This is the standard PDP-8 peripheral design pattern (devices like the PT08
KL8E used 74174/74175 latches for exactly this reason) and translates well
to a microcontroller-based implementation.

### 5.3 Latch part choice

74AHC574 is suggested: 8-bit edge-triggered (positive-edge), tri-state,
~5 ns clock-to-output, 3.3 V compatible. Two 574s in parallel form the
12-bit latch (8 + 4 bits used). Alternative: 74AHC373 (transparent
latch) if level-sensitive behaviour is preferred. AHC family chosen for
3.3 V compatibility on the RP2350 side; the bus side is buffered by the
74244/74540 already so 5 V tolerance there is irrelevant.

For the IOT response latch, only 4 bits are used (SKIP, C0, C1, C2) so a
single 74AHC574 covers it with 4 spare positions usable for break-cycle
participation or other response bits.

### 5.4 Latch-enable demultiplexing

The shared input-OE (`OE_IN`) and output-LE (`LE_OUT`) RP2350 pins each
drive both an MD-side and a DATA-side latch through a small two-channel
demultiplexer. The demux input selector is the cycle qualifier:
`MEM_START` routes the pulse to the MD-side latch, `IO_PAUSE` routes it
to the DATA-side. A `SN74AHC1G126` single tri-state buffer pair (or two
`74AHC08` AND-gate channels) implements each demux. Cost: one tiny
SOT-23 part per demux, two demux instances total. This frees two
otherwise-dedicated RP2350 GPIOs at minimal hardware cost.

## 6. Timing Requirements and PIO Implementation

### 6.1 PDP-8/E Omnibus timing (nominal)

Quantities below are taken from the PDP-8/E Maintenance Manual. Exact
numbers vary by CPU model; the design is built to the slowest-tolerated
margins.

| Phase | Duration (approx.) | Signals asserted |
|---|---|---|
| TS1 | 0 — 200 ns | MA valid, MD = IOT instruction (during IOT cycles), MEM_START asserted |
| TS2 | 200 — 700 ns | Memory read-out on MD; IOT decode window |
| TS3 | 700 — 1000 ns | Data manipulation; DATA-bus transfer at BUS_STROBE |
| TS4 | 1000 — 1500 ns | Write-back; cycle complete |

Critical setup/hold requirements:

| Path | Setup before strobe | Hold after strobe |
|---|---|---|
| MA valid before STROBE | ≥ 200 ns | ≥ 50 ns |
| MD valid before STROBE (read) | ≥ 80 ns | ≥ 50 ns |
| MD valid at WRITE edge | ≥ 50 ns | ≥ 100 ns |
| DATA valid at BUS_STROBE | ≥ 80 ns | ≥ 100 ns |
| IOT response (C0/C1/C2/SKIP) at TP2 | ≥ 50 ns | ≥ 100 ns |

Total cycle time: ~1.5 µs, giving an Omnibus toggle rate of ~660 kHz.

### 6.2 RP2350 clock domain

PIO is clocked at the system clock divided down. We run the system clock at
150 MHz (one cycle = 6.67 ns). PIO `wait` and `in/out` instructions execute
in one PIO clock each, so end-to-end "edge to RP2350-internal-FIFO" latency
is well under 20 ns.

In one Omnibus cycle (1.5 µs) PIO executes ~225 instructions. There is
ample time to capture, decode, and respond.

### 6.3 PIO state-machine allocation

RP2350 has 3 PIO blocks × 4 SMs each = 12 SMs. The card uses:

| PIO.SM | Role |
|---|---|
| PIO0.SM0 | Memory cycle FSM |
| PIO0.SM1 | Address sampler — captures MA on TS1 edge into a FIFO |
| PIO0.SM2 | Memory write capture — captures D from MD-IN latch on WRITE edge |
| PIO1.SM0 | IOT cycle FSM |
| PIO1.SM1 | IOT decode helper — captures MD-IN at IOT cycle TS1 into a FIFO |
| PIO1.SM2 | DATA bus capture — samples DATA-IN at BUS_STROBE when sinking |
| PIO2.SM0 | TS edge sequencer — exposes a 4-state phase counter via IRQ flags |
| PIO2.SM1 | Trace shifter — clocks 32 bits out of the 74HC597 chain during TS2 of each cycle (§6.10) |
| PIO2.SM2 | Trace fast-path snapshot — samples direct GPIOs on the same TS1 IRQ (§6.10) |

Three SMs spare for future device emulations that need their own
protocol state machines (e.g., a DMA-capable disk controller using
BREAK cycles).

### 6.4 Memory READ cycle — sequence

```
  CPU                          RP2350 (PIO0.SM0 + Cortex-M33)
  ---                          --------------------------------
  Asserts MEM_START at TS1
  MA valid                ──→  PIO0.SM0 wakes, samples MA + EMA at TS1
                               Pushes word-address into RX FIFO
                          ←──  M33 Core 0 picks up address, fetches from SRAM
                               Pushes 12-bit data into TX FIFO
  TS2 begins              ──→  PIO0.SM0 pulls data, drives RP2350 D port,
                               pulses LE_MD_OUT (clocks data into MD_OUT latch)
                               Asserts MD_DIR (enables 74540 to drive MD bus)
  STROBE                  ──→  CPU samples MD; MD_OUT latch is holding valid data
  TS4 ends                ──→  PIO0.SM0 deasserts MD_DIR; cycle complete
```

Worst-case latency from MEM_START to MD valid on bus:

| Step | Time |
|---|---|
| MEM_START → PIO sample MA | 1 PIO cycle = 6.67 ns |
| FIFO push → DMA → M33 wake | ~30 ns |
| SRAM fetch (single-cycle at 150 MHz) | 6.67 ns |
| FIFO return → PIO out | ~30 ns |
| RP2350 GPIO → 74AHC574 setup → output | ~10 ns |
| 74AHC574 output → 74540 → MD pin | ~15 ns |
| **Total** | **≈ 100 ns** |

TS2 begins ~200 ns after MEM_START, so we have roughly 100 ns of margin
before STROBE could be asserted. Comfortable.

### 6.5 Memory WRITE cycle — sequence

```
  CPU                          RP2350 (PIO0.SM0/SM2 + M33)
  ---                          --------------------------------
  Asserts MEM_START at TS1
  MA valid                ──→  PIO0.SM0 samples MA, pushes to FIFO
  CPU drives MD with data
  WRITE strobe asserted   ──→  74AHC574 MD_IN latches MD on WRITE trailing edge
                               PIO0.SM2 wakes on WRITE, asserts OE_MD_IN
                               Reads D port, pushes (MA,data) to write FIFO
                          ←──  M33 Core 0 commits to internal SRAM
  Cycle ends
```

The critical path is "WRITE asserted → latch captures MD". 74AHC574
clock-to-Q is < 10 ns. The MD signal is valid by spec at WRITE assertion
with a typical hold time of ≥ 100 ns, well in excess of the latch's
required 5 ns hold.

### 6.6 IOT cycle — sequence

```
  CPU                          RP2350 (PIO1.SM0/SM1 + M33)
  ---                          --------------------------------
  Asserts IO_PAUSE at TS1
  MD bus carries IOT instr ──→ PIO1.SM1 captures MD-IN latch contents:
                                bits 3..8 = device code
                                bits 9..11 = operation
                               Push to RX FIFO
  TS2 (IOT decode window) ←──  M33 dispatch table lookup:
                                handler[device_code][operation]
                                produces (SKIP, C0, C1, C2) and DATA-out
                               Writes 4-bit response → IOT response latch
                               via LE_IOT_OUT
                               Writes 12-bit DATA → DATA_OUT latch via
                               LE_DATA_OUT (only if C2 says we source)
                               Asserts OE_IOT_RESP (gates 74540 to drive bus)
  TP2                     ←──  IOT response visible to CPU; CPU records
                               (skip / clear AC / load AC / etc.)
  BUS_STROBE              ←──  Card drives or samples DATA, depending on
                               C-code. PIO1.SM2 handles the timing:
                                if sourcing: 74540 DATA_OUT enabled
                                if sinking: latch captures DATA at strobe
                                edge; M33 reads and updates device state
  IO_PAUSE deasserted     ──→  Card disables 74540 outputs, returns to idle
```

The tightest path here is **MD → device-code lookup → IOT response valid
at TP2**, a window of ~400 ns from IO_PAUSE assertion to TP2.

| Step | Time |
|---|---|
| IO_PAUSE → PIO sample MD-IN | 6.67 ns |
| FIFO → M33 wake | ~30 ns |
| Dispatch table lookup (single load) | ~10 ns |
| Compute response (table-driven for trivial IOTs) | ~10–100 ns |
| FIFO out → LE_IOT_OUT pulse | ~30 ns |
| Latch CK→Q, 74540 prop | ~15 ns |
| **Total** | **≈ 100–200 ns** |

200 ns of margin. Devices with non-trivial IOT semantics (e.g., reading a
character from a deep ring buffer) still finish within the budget; complex
operations queue work for the M33 to handle in the slack between IOTs.

### 6.7 Interrupt response

When an emulated device needs to interrupt:

1. M33 firmware sets a flag.
2. Background task asserts INT_RQST GPIO (open-drain emulation —
   see below).
3. CPU acknowledges via INT_IN_PROG (observed via the §6.10 trace
   chain at full bus rate).
4. CPU executes IOT to clear the device's interrupt flag.

INT_RQST is on direct GPIO because deassertion is timing-coupled to the
acknowledging IOT — the firmware deasserts it within the IOT cycle that
acknowledges it, which would not be reliable at I²C latencies.

**Why INT_IN_PROG and INT_STROBE are not on direct GPIO.** The card
has exactly two cycle-deadline obligations around interrupts: assert
`~INT_RQST` when its emulated device wants to interrupt, and deassert
it during the IOT cycle in which the OS clears that device's flag
(KCF, TCF, …). Both are handled on the fast path — `~INT_RQST`
directly on GPIO, the IOT via the §6.6 dispatch path. INT_IN_PROG and
INT_STROBE, in contrast, are CPU-internal signals announcing the
interrupt-entry sequence ("PC → location 0, jump to location 1, clear
ION") to the bus; the card has no edge-triggered action on them. They
are captured by the §6.10 trace chain on every Omnibus cycle, which
is enough for status display ("interrupt being serviced") and full
trace reconstruction — what the card cannot do is fire a PIO state
machine off their edges, which it does not need to. This matches the
standard PDP-8 software model: interrupt dispatch is done by the OS
via skip-on-flag IOTs, not by hardware-vectored response to
INT_STROBE.

**Open-drain emulation with a tri-state buffer.** ~INT_RQST is a
wire-OR signal on the Omnibus: any card may pull it low, the bus
terminator pulls it high, and an open-collector / open-drain driver is
the canonical way to drive it. The 74540 is a tri-state (push-pull)
buffer, not open-collector, so the firmware emulates open-drain
behaviour by holding the corresponding 74540 input permanently at the
asserting level and toggling only the channel's output enable: OE low
drives the bus low, OE high goes to high-Z (the bus pull-up wins).
The 74540 output never actively drives high, so no contention can
occur with another card asserting ~INT_RQST in parallel.

### 6.8 Console-cycle timing

Console operations originate from the host via CDC0 and are therefore
asynchronous to the running PDP-8. The firmware sequences them as
multi-step operations spanning hundreds of microseconds:

1. **Take control** — assert KEY_CTL + STOP via MCP23017 (~300 µs I²C
   round-trip). Wait for the CPU to actually halt (observe RUN go low,
   typically within one machine cycle = 1.5 µs after STOP is sampled).
2. **Set up SR / control gates** — drive D-port, pulse LE_OUT, assert
   LA_ENABLE / DF_ENABLE / CPMA_DISABLE via MCP23017 + OE_CONSOLE.
3. **Pulse-timed step** — pulse LOAD_CONT or PULSE_LA via direct GPIO
   under PIO control. Pulse width ~200 ns; PIO-generated, so width is
   exact regardless of M33 activity.
4. **Force a memory cycle** (for examine/deposit) — pulse MEM_START via
   direct GPIO. Card's own memory cycle FSM (§6.4/6.5) handles the rest.
5. **Release control** — flip MCP23017 #2 pins back to inputs, deassert
   OE_CONSOLE. Release STOP if user requested run/continue.

Total console operation time: ~1 ms dominated by I²C transactions for
set-and-hold signal management. The pulse-timed bus operations themselves
are nanosecond-scale and meet PDP-8/E timing margins easily because the
CPU is halted while the operation runs.

### 6.9 BREAK / DMA cycles

The base firmware does not participate in BREAK cycles. The card observes
BRK_IN_PROG and BREAK_CYCLE via the §6.10 trace chain at full bus rate
and stays out of the way. A device emulation that needs BREAK
participation (e.g., a disk controller doing three-cycle data break)
extends the design by:

* Promoting BRK_IN_PROG / BREAK_CYCLE to direct GPIO (swapped out
  from a less-critical fast pin — see §4.3),
* Using one of the spare PIO state machines for the BREAK protocol,
* Driving MA/MD via the existing latches under BREAK timing rules.

### 6.10 Cycle-accurate bus tracing

To eliminate the slow-path observation gap (§4.2 was originally
limited to ~50 Hz for major-state, IR, link, break, interrupt-
acknowledge, and TPx signals), the card includes a high-speed shift-
register chain that captures all 32 of those signals on every Omnibus
cycle. Combined with the existing fast-path GPIO snapshot, this gives
the card logic-analyser-grade visibility — any of the 96 active
Omnibus signals is observable at every cycle, with no external
instrument needed.

#### 6.10.1 Hardware: 4× 74HC597 chain + 74HC273 pulse latch

Four 74HC597 8-bit parallel-load shift registers are daisy-chained
(QH of one feeds DS of the next) to give 32 captured bits per cycle.
The 74HC597 is a *dual-stage* part — a parallel-loaded **storage
register** clocked by RCK feeds an independently-clocked **shift
register** clocked by SHCP. This decouples capture (must be
synchronous to the bus) from readout (free-running PIO), and is the
key reason for choosing 597 over the simpler single-stage 74HC165.

Pulse and phase signals — TP1, TP2, TP3, TP4, INT_STROBE, LINK_LOAD,
INHIBIT, RETURN — are short and asynchronous to a single end-of-cycle
sample point. They feed a **74HC273 octal D-FF with asynchronous
/CLR** that acts as an 8-bit pulse-latch bank: D inputs tied high,
CLK input is the pulse signal itself, /CLR is a brief reset pulse
generated by an RC differentiator off TS1-rising. Each Q goes high
the moment its pulse rises and stays high until the next /CLR pulse
clears it at the start of the following cycle. The 74HC597 storage
register samples the Q outputs at the TS1-rising edge of each cycle
— before the /CLR pulse fires — so any pulse that asserted during the
preceding cycle is captured as Q=1 in that cycle's trace record.

Inputs to the 597 chain (suggested mapping — bit positions are not
firmware-visible; the firmware reads a 32-bit shift result and
masks/shifts according to a constant):

| 597 # | Inputs | Source | Group |
|---|---|---|---|
| #A | F, D, E, F_SET, IR00, IR01, IR2, USER_MODE | direct from 74244 | Major state + IR top bits — all level signals |
| #B | LINK, LINK_DATA, OVERFLOW, RUN, NOT_LAST_TR, ROM_ADDR, INTERNAL_IO, SOURCE | direct from 74244 | CPU register state + demoted fast signals (§4.3) — all level signals |
| #C | BREAK_CYCLE, BRK_IN_PROG, BRK_DATA, NTS_STALL, INT_IN_PROG, POWER_OK, SW, (1 spare) | direct from 74244 | Break / interrupt status — all level signals |
| #D | **TP1, TP2, TP3, TP4, INT_STROBE, LINK_LOAD, INHIBIT, RETURN** | **74HC273 Q outputs** | Pulse and phase signals — latched by the 74HC273 |

Inputs to the 74HC273 pulse-latch (8-bit):

| 273 bit | Source | Why latched |
|---|---|---|
| Q0..Q3 | TP1..TP4 | ~100 ns pulses fired at fixed phase offsets within the cycle; would otherwise be missed by single-snapshot sampling |
| Q4 | INT_STROBE | short pulse during interrupt entry |
| Q5 | LINK_LOAD | short pulse when LINK is loaded by a CPU operation |
| Q6 | INHIBIT | memory-cycle phase signal asserted during inhibit phase only — would have deasserted by sample time |
| Q7 | RETURN | memory-cycle phase signal at end-of-cycle, similarly transient |

The 74HC273's Q outputs are stable from the moment the pulse fires
until the next /CLR — so the 597 storage register, sampling at the
following cycle's TS1-rising, sees a consistent "did this signal
assert during the previous cycle" indicator for every pulse signal.
Fine pulse timing within a cycle is *not* recovered (the latch
doesn't preserve when in the cycle the pulse fired), but for trace
analysis the answer to "did TP3 fire on this cycle" is what's
needed; pulse position within the cycle is fixed by the PDP-8/E
timing model (§6.1).

#### 6.10.2 Capture timing

  * **74HC597 RCK** = buffered TS1 (positive-true). On TS1-rising,
    each chip's storage register clocks in its 8 parallel inputs.
    This sample point captures the *previous* cycle's accumulated
    state — for level signals (#A, #B, #C) the value is whatever
    was on the input at TS1-rising; for pulse signals (#D), the
    74HC273's latched Q values reflect any pulse that fired during
    the previous cycle.
  * **74HC273 /CLR** = brief LOW pulse derived from TS1-rising via
    an RC differentiator (1 kΩ + 100 pF ⇒ ~100 ns pulse), arranged
    so the /CLR transition follows the 597 RCK transition by
    ≥ 5 ns to satisfy the 597's setup/hold without race.
    Implementation: a single 74AHC1G14 Schmitt-trigger inverter
    cleans up the differentiated edge.
  * **74HC597 /STR** = buffered TS1 inverted. On TS1-falling
    (= start of TS2), /STR rises and copies the storage register
    contents into the shift register; PIO can then begin shifting.
  * **74HC597 SHCP** = TRACE_SCK from PIO2.SM1, clocked at
    sysclk/2 = 75 MHz. 32 bits at 13.3 ns each = ~427 ns total —
    completes within the TS2..TS4 window (1300 ns available).
  * **74HC597 QH (last in chain)** → TRACE_SDI to RP2350.

This timing means each trace record corresponds to the *just-
finished* cycle: when cycle N's TS1 rises, we capture state from
cycle N-1. The firmware accounts for this one-cycle offset by
pairing the 597-shifted slow-signal record with the *previous*
fast-path snapshot in the assembly path (§6.10.3).

#### 6.10.3 PIO and DMA path

Two PIO state machines on PIO2 (currently free) handle capture:

| PIO.SM | Role |
|---|---|
| PIO2.SM1 | Trace shifter — clocks TRACE_SCK 32 times per cycle, reads QH of #A into ISR, pushes 32-bit slow-signal word into RX FIFO |
| PIO2.SM2 | Fast-path snapshot — on the same TS1 IRQ, samples a configurable 32-bit slice of direct GPIOs (MA + EMA + cycle qualifiers + a few extras) and pushes into a parallel RX FIFO |

A DMA channel pair joins the two 32-bit FIFO outputs into a single
64-bit (8-byte) trace record and writes it into a circular ring
buffer in SRAM. The ring sink is software-configurable.

Per-cycle PIO time:

* Snapshot trigger — TS1 rising edge, raised as IRQ by the §6.3
  PIO2.SM0 phase counter. The 74HC597 storage register has already
  captured by hardware (RCK = TS1).
* PIO2.SM1 waits for the TS1-falling edge (start of TS2), then
  begins shifting at sysclk/2 (= 75 MHz, 13.3 ns per bit) —
  32 bits × 13.3 ns = ~427 ns to complete the shift. The 74HC597's
  /STR has just risen on the same TS1-falling, copying the storage
  register into the shift register so PIO sees stable data.
* The shift completes well within TS2 (~500 ns), leaving TS3 and
  TS4 idle on the trace path.
* PIO2.SM2 takes the parallel fast-path snapshot of direct-GPIO
  signals on the same TS1-rising IRQ in 1 PIO cycle and pushes
  immediately.

#### 6.10.4 Ring buffer + trigger

The trace ring buffer's size and trigger mode are configurable from
CDC0. Sensible defaults:

| Mode | Behaviour |
|---|---|
| `ring` | Continuous capture into a 256 KB ring (32k × 8 B = ~50 ms at peak Omnibus rate). Always recording; oldest overwritten. |
| `trigger <expr>` | Capture starts when `expr` matches. Pre/post-trigger split configurable. |
| `match <expr>` | Capture only cycles where `expr` matches (sparse log). |
| `single` | One-shot: capture until ring full, then stop. |

Trigger expressions reference any captured signal by name — e.g.
`MEM_START & MA == 07777`, `IO_PAUSE & device == 03`, `INT_RQST.rise`,
`BRK_IN_PROG.fall`. Expression evaluation runs on the M33 in the
gap between PIO interrupts.

Console interface:

```
  > trace start [ring | trigger <expr> | match <expr> | single]
  > trace stop
  > trace dump [count] [text|binary]   — bulk readout via CDC0
  > trace save <name>                  — flush ring to SD card (§7.6)
  > trace clear
```

Bulk binary dump over CDC0 streams at full USB speed (~1 MB/s).
A 256 KB ring takes ~256 ms to dump.

#### 6.10.5 Halted-CPU behaviour

TS1 does not fire when RUN is low, so the trace chain stops
capturing new samples. This is acceptable because once the CPU
halts, the slow signals it owns (F/D/E, IR, LINK, USER_MODE,
NOT_LAST_TR, RUN itself, …) are static — the most-recent trace
record from the last running cycle reflects the current bus state
correctly. Console-status queries read the head of the trace ring
buffer for those signals.

The card-driven slow signals — set-and-hold console outputs and
housekeeping LEDs (§4.2) — are independently visible to the firmware
through the MCP23017 path; halt does not affect them.

When the host issues a `run` or `step` command and the CPU resumes,
TS1 fires again and the trace chain captures the resumed activity
on the very first cycle.

#### 6.10.6 Cost / I²C effect

* **+4× 74HC597** @ ~$0.50 each = +$2.00 BOM.
* **+1× 74HC273** octal D-FF (pulse-latch bank) ~$0.30.
* **+1× 74AHC1G14** Schmitt-trigger inverter (cleans up the RC-
  differentiated /CLR pulse) ~$0.12, plus an RC pair (1 kΩ + 100 pF)
  in the passives kit.
* **−2× MCP23017** @ $1.62 each = −$3.24 BOM (the two observe-only
  expanders at 0x20/0x21 are deleted; their signals are now in the
  trace chain).
* **Net board cost**: −$0.82 vs. the pre-trace design.
* **I²C bus loading**: 2× MCP23017 + up to 4× SC16IS740 = 6 devices,
  leaving generous headroom for SC16IS740 byte transfers at sustained
  RS-232 throughput.
* **Firmware**: a few hundred lines for the PIO program, ring-buffer
  manager, and CDC0 trace shell — small relative to the device-
  emulation code.

## 7. USB Architecture

### 7.1 Composite CDC ACM device

The RP2350 enumerates as a single USB device with several CDC ACM functions.
TinyUSB (the USB stack shipped with the Pico SDK) supports composite
configurations natively.

| CDC # | Purpose | Host appears as |
|---|---|---|
| CDC0 | Console / control port | /dev/ttyACM0 |
| CDC1 | Primary serial (PT08, devices 03/04) | /dev/ttyACM1 |
| CDC2 | Secondary serial (KL8E, configurable device codes) | /dev/ttyACM2 |
| CDC3 | Tertiary serial | /dev/ttyACM3 |
| ... | ... | ... |

Default configuration: 4 CDC ports (1 console + 3 serial). The USB
descriptor table is a compile-time setting.

### 7.2 Console / control protocol (CDC0)

Line-oriented ASCII protocol for human use; binary mode for tooling.

```
  > help
  examine <octal-addr>           — read one word
  deposit <octal-addr> <value>   — write one word
  dump <octal-addr> <length>     — dump memory range
  load <format>                  — upload memory image (RIM, BIN, hex, raw)
  save <format>                  — download memory image
  field <0-7>                    — set/show current EMA field
  run                            — release HALT
  halt                           — assert HALT (via STOP signal)
  step                           — single-step (via SS)
  status                         — show CPU state from latest §6.10 trace sample
  trace <subcommand>             — control the cycle-accurate trace ring (§6.10)
  device list                    — list registered emulated devices
  reset                          — assert INITIALIZE on the bus
  ...
```

Binary upload uses a length-prefixed framed protocol so the host can stream
core images at full USB speed (~1 MB/s, far faster than RIM/BIN tape).

### 7.3 Emulated serial peripherals (CDC1+)

Each CDC port maps to a pair of device codes (input device + output device).
For PT08-class peripherals:

* Input device (e.g., 03 for keyboard): IOTs are KSF (skip on flag), KCF
  (clear flag), KRS (read static), KRB (read and clear).
* Output device (e.g., 04 for teleprinter): IOTs TSF (skip on flag), TCF
  (clear flag), TLS (load and start), TPC (load static).

The firmware maintains, per CDC port:

* An RX ring buffer (host → Omnibus): bytes written to the host CDC
  endpoint enter the ring; the next KRB/KRS IOT consumes them.
* A TX ring buffer (Omnibus → host): bytes from TLS/TPC IOTs enter the
  ring and are delivered to the host CDC endpoint.

Baud rate is honoured at the IOT-flag level (the keyboard/teleprinter flags
go up at the configured rate even though USB carries data at full speed).
This preserves the timing behaviour of programs that depend on serial
delays.

### 7.4 Optional physical RS-232 ports

Some workloads need real RS-232 (paper tape readers, hardware modems,
serial-to-IBM-3270 gateways, vintage terminals that USB-CDC can't reach).
The card carries footprints for **up to four optional asynchronous
serial ports** that connect emulated PDP-8 serial devices to physical
RS-232 instead of (or in addition to) the USB CDC ports of §7.1.

**Topology — modular per-port**

```
  Emulated PT08/KL8E (firmware)
         |
         | (in-firmware FIFO)
         |
       RP2350
         |
         | I²C0 (shared with MCP23017s, 1 MHz fast-mode-plus)
         |
   +-----+-----+-----+-----+
   |     |     |     |     |
   v     v     v     v     v
  SC16IS740   ...   ...   SC16IS740     ←  populate 1, 2, 3, or 4
   |     |     |     |     |
   v     v     v     v     v
  MAX3232    ...   ...   MAX3232        ←  one per populated UART
   |     |     |     |     |
   v     v     v     v     v
   DB9   ...   ...        DB9           ←  one per populated UART
```

**Chip choice — 4× SC16IS740 single-channel I²C UART** (one chip per
port). Each SC16IS740 is a 16-pin TSSOP, ~$2.50, with a 64-byte
hardware FIFO per direction and full RS-232 flow control (RTS/CTS).
The A0/A1 address straps give four distinct I²C addresses
(0x48, 0x49, 0x4A, 0x4B), so up to four SC16IS740s share the bus
without conflict.

**Why per-port chips rather than one quad-UART**: lets the user populate
exactly as many ports as needed — 1, 2, 3, or all 4 — without paying
for unused channels. Total cost for four ports is ~$10 in UART silicon
(vs ~$30 for a single MAX14830). Each chip carries its own crystal
load capacitors and can use either a shared 14.7456 MHz on-board
crystal/oscillator or per-chip clocks.

**Level shifting — MAX3232 (or SP3232) per populated port**:
3.3 V supply, internal charge pump (no ±12 V rail needed), 2 drivers
+ 2 receivers — exactly enough for TX/RX/RTS/CTS on a fully handshaked
DB9. One MAX3232 per active port; depopulated ports leave the
SC16IS740 footprint and the MAX3232 footprint both empty.

**Connectors**: right-angle DB9 male PCB connectors at the card's
external edge, or alternatively 2×5 IDC pin headers with off-board DB9
pigtails. Headers save board area; DB9s save cabling. Both are footprint
options on the PCB, populated as needed.

**I²C bus loading**: 4 SC16IS740s + 2 MCP23017s = 6 devices on the bus.
At 1 MHz fast-mode-plus, byte transfer latency is ~24 µs. For the
heaviest realistic load — 4 ports × 115.2 kbaud × ~12 kHz byte rate =
48 kHz aggregate — the bus is < 25% utilised, leaving plenty of
headroom for MCP23017 polling.

**Firmware integration**: each emulated serial peripheral (PT08, KL8E,
or future device) has a configurable backend: USB-CDC, an SC16IS740
channel, or both (split — host receives via CDC, peripheral sends
RS-232). The firmware mapping is set per peripheral via the CDC0
console:

```
  > serial map kl8e0 cdc1
  > serial map kl8e1 sc16is740:0x48,9600,8N1,rts/cts
  > serial map kl8e2 both:cdc2,sc16is740:0x49
```

**Optional population**: the SC16IS740s, MAX3232s, and DB9 connectors
are not required for memory + console + USB-CDC operation. Boards
intended for software-only emulation can leave the entire RS-232
sub-circuit unpopulated. Cost increment is roughly $5 per populated
port (UART + transceiver + connector).

### 7.5 Adding device emulations

Adding a device is firmware-only:

1. Define the device codes (one or more 6-bit codes).
2. Implement IOT handlers as functions returning `(skip, c0c1c2, data)`.
3. Register the handlers in the dispatch table at boot.
4. Optionally allocate an additional CDC port for host-side data flow
   (e.g., disk-image read/write) or use the console port for control.
5. Optionally arrange a background task to participate in interrupts /
   BREAK cycles.

The dispatch table is a single static array indexed by `(device << 3) |
operation`, giving 512 entries. Unimplemented entries point to a default
handler that asserts no response.

### 7.6 SD card storage

A microSD socket is included on-board for bulk storage. It serves the
emulated disk and tape devices (RX01, TC08, …), holds memory image
archives larger than the on-chip flash region, and provides a
removable-media path for moving disk images between cards or hosts.

**Interface**: 4-bit SPI on a dedicated SPI controller (`SPI0` or
`SPI1`) of the RP2350. Pins:

| Pin | Net | Direction |
|---|---|---|
| `SD_MOSI` | DI on SD card | RP2350 out |
| `SD_MISO` | DO on SD card | RP2350 in |
| `SD_SCK`  | CLK on SD card | RP2350 out |
| `SD_CS`   | CS on SD card | RP2350 out |

`CD` (card detect) and optional `WP` (write protect) connect to spare
GPIO on MCP23017 #3.

**Voltage**: SD cards run at 3.3 V — no level shifting needed.

**Speed**: SPI bus runs at up to 25 MHz (the PIO can also drive faster
SDIO 1-bit mode if needed later, but standard SD-SPI is plenty for
emulating period-correct disk and tape devices).

**GPIO budget**: the 4 pins for SD-SPI are funded by folding the
console pulse outputs into the IOT-response latch path (§4.4). The
direct-GPIO pin count rises by exactly 1 vs. the no-SD design.

**Filesystem**: FatFS or LittleFS — the user picks per the host
interoperability they want. FatFS is the obvious choice for sharing
with PCs; LittleFS is more robust to power-loss and works fine if disk
images are only ever swapped via the USB CDC0 console.

**Use cases**:

* RX01 floppy emulation: each `.rx01` file is a 252 KB image; one SD
  card holds thousands.
* TC08 DECtape emulation: each tape image is up to 96 KB.
* Memory snapshots: full 32 KW core image is 64 KB per snapshot.
* Boot loader staging area: the firmware can autoload a named image at
  boot from a configured path on SD.

## 8. Memory Model and Storage

* RP2350B has 520 KB SRAM.
* PDP-8 word size is 12 bits; each word is stored in a `uint16_t` (16 bits,
  2 bytes per word).
* 32 KW × 2 B = 64 KB for the full 8-field address space.
* A separate 32 KW shadow (another 64 KB) provides ROM emulation gated by
  `ROM_ADDR`.
* Total memory budget: ~128 KB out of 520 KB, leaving room for
  device-emulation buffers, USB queues, etc.

Persistence: the on-board QSPI flash on the PGA2350 holds firmware in one
partition and an LFS-formatted region for configuration, saved memory
images, and disk-image storage for any disk-emulation devices. Saving a
32 KW image to flash takes < 100 ms.

## 9. Bring-Up Plan

1. **Power and clock.** Verify 3.3 V regulation, USB enumeration, status
   LED toggle via MCP23017 #3.
2. **I²C bus.** Verify both MCP23017s respond at 0x22/0x23; toggle
   IND1/IND2 LEDs from firmware (now on MCP23017 #2 spare positions).
3. **Trace chain.** Plug the card into a running PDP-8/E with all
   74540 outputs disabled. With the CPU running, start the §6.10
   trace and verify the captured RUN, F/D/E, IR, LINK fields match
   the actual program execution. Then halt the CPU and verify the
   periodic-strobe fallback (§6.10.5) keeps the trace updated.
4. **Bus passive.** With all 74540 outputs still disabled, confirm
   the card is transparent to the bus — no contention, no spurious
   edges.
5. **Address sampling.** Enable PIO0.SM1; verify MA + EMA captured
   correctly for each instruction the running CPU executes (compare
   against expected PC walk; cross-check against trace output from
   step 3).
6. **Memory READ emulation, single field.** Disable any other memory
   in the slot; load a small program into RP2350 SRAM; enable the
   memory READ path. CPU should fetch from the card.
7. **Memory WRITE emulation.** Enable WRITE capture path; verify
   writes land in the SRAM image.
8. **Extended-memory cycles.** Run a CDF/CIF sequence; confirm EMA
   is sampled per-cycle and addresses route to the correct field.
9. **IOT decode.** Implement a single trivial IOT (e.g., one that
   just returns SKIP); verify CPU behaviour.
10. **Console CDC.** Bring up CDC0; implement examine/deposit;
    verify the host can manipulate memory.
11. **Console-mode bus drives.** Validate the §4.4 set-and-hold +
    pulse paths with the CPU halted: assert KEY_CTL, set CPMA via
    SR-on-DATA + LOAD_CONT, examine memory through forced cycles.
12. **Serial CDC.** Bring up CDC1 with PT08 emulation; load FOCAL or
    BASIC; verify a TTY session works.
13. **Multi-CDC.** Add additional CDC ports.
14. **Soak test.** Run a memory-stress program for hours; verify no
    timing-related corruption.

## 10. Open Questions and Risks

* **EMA sampling alignment.** EMA0..EMA2 are sampled on the same TS1 edge
  as MA. If the buffer/wiring delay on the EMA path differs materially
  from the MA path, the captured field could correspond to a different
  cycle than the captured address. Mitigation: route EMA through the same
  74244 bank as MA (or one with matched propagation delay), and verify
  with a logic-analyser capture during bring-up step 5.
* **Polarity correctness.** 74540 inverts; 74244 does not. The firmware
  must carry the polarity convention consistently. A polarity-inversion
  layer at the GPIO read/write boundary keeps the rest of the firmware in
  positive-true logic.
* **AHC/AHCT edge speeds on the Omnibus backplane.** The AHC/AHCT
  family has transition times of ~2 ns. The PDP-8/E backplane was
  designed for the slower 74H/74S TTL drivers of its era (transition
  times ~5–10 ns) and is not a controlled-impedance / terminated
  transmission line. Fast-edged drivers on long unterminated traces
  can ring and produce reflections that cause spurious edge detection
  on neighbouring cards. Mitigation: provide footprints for 33–47 Ω
  series resistors in every 74540 output channel that drives directly
  to a card-edge contact, populated only if ringing is observed during
  bring-up step 4. As a fall-back, the slower 74HC family (transition
  times ~6 ns) is logic-compatible — a BOM swap, no schematic change.
* **74540 OE timing for IOT response.** The IOT response 74540 must be
  enabled exactly between TP1 and TP4 of the IOT cycle. Combinational gate
  in front of OE driven by `IO_PAUSE & TS2_or_TS3` is straightforward.
* **MCP23017 polling latency.** 2 remaining chips × 16 bits each at
  1 MHz fast-mode-plus I²C ≈ 80 µs round-trip. Acceptable for the
  console set-and-hold and housekeeping use cases. Firmware must
  avoid blocking on it on the main thread.
* **Power sequencing.** RP2350 must come up before it tri-states its
  GPIOs — with reset asserted, the card outputs to the bus must be
  disabled. The 74540 OE pins are pulled high (disabled) by default; the
  RP2350 actively asserts them low when it is ready.
* **Coexistence with other Omnibus memory.** If the PDP-8/E backplane
  also has core or other semiconductor memory in another slot, the
  emulated memory must be addressed in non-overlapping fields. The
  console `field` command configures which fields the card answers at
  runtime.
* **SOURCE direction (open).** The PDP-8/E memory cycle has the
  addressed memory module assert `SOURCE` to indicate "data on MD is
  valid" — which on this card would be an RP2350 output through the
  74540 bank. Two questions need verification against the schematic and
  PDP-8/E maintenance manual before final routing:
  (a) Is `SOURCE` driven by the addressed memory module (so we drive it
  when the cycle hits our address range and observe it otherwise — i.e.
  bidirectional path with input via 74244 and output via 74540), or
  driven exclusively by the CPU/timing-generator (in which case it's
  RP2350-input only)?
  (b) If we drive it: what is the precise gating — `MEM_START &
  address-in-our-range & ~WRITE & TS2..TS3`?
  Until this is resolved, `GP_SOURCE` is marked TBD in Appendix A and
  the corresponding 74244/74540 channel pair (bidirectional path) is
  reserved on the PCB.
